# 01 · 架构与数据流

> 状态：目标设计，非当前全量实现。已实现部分及代码入口见[能力状态](./02-能力状态.md)。

## 一次任务经过哪些门

```text
入口 CLI / 以后更多 Channel
  → 身份、会话、原始目标与授权范围
  → 任务判断：回答 / 检索 / 计划 / 执行 / 先澄清
  → Task Profile：任务阶段、证据源、可用能力、完成契约
  → sonic Core：RunState、上下文、预算、事件、停止与恢复
      ↔ Provider：只产生回答或工具提案
      → ToolRuntime：校验 → 权限/审批 → 隔离执行 → 结果对账
  → Verifier：检查任务证据
  → 答复：完成 / 失败 / 未验证 / 需用户处理
```

当前代码只包含其中的教学子集：FakeProvider、运行循环、事件/状态、示例工具与固定文本完成契约。没有正式 Channel、Task Profile、真实模型、沙箱、恢复执行或 RepoFix Verifier。

## 各层承担的责任

**会话与 Run。** 一次会话可有多个 Run。Run 有独立预算、状态和最终证据；会话只引用对话、身份和许可，未来记忆不应伪装为 RunState。当前代码只有独立 Run 的教学实现，没有会话管理。

**Task Profile。** 它描述 `task_schema`、`stage_plan`、`context_sources`、`tool_manifests`、`policy_scope`、`completion_contract` 和 `eval_suite`。RepoFix 与资料研究应换 Profile，不改事件与副作用语义。这还是目标接口。

**Core。** Core 管通用请求、模型提案、动作、观察、预算、取消、事件和终态。权威运行事实不应仅放在模型消息数组里。当前 `RunState` 可由 SQLite 事件重建，但还不能把未完成 Tool 安全续跑。

**Provider。** 模型回答是建议。其工具参数必须校验，不得凭自然语言绕过权限。当前 `FakeProvider` 支持确定性测试，尚无真实 Provider、流式响应和 token/费用账本。

**ToolRuntime 与 Safety。** Registry 管可发现的工具；策略决定能否调用；审批绑定具体动作；隔离限制实际资源；外部效果记录用于重试前对账。当前只有简单 Registry、路径段拒绝样例和同进程内存 EffectJournal，远非生产安全层。

**Verifier。** 模型的结束消息只是候选答案。不同任务有不同证据：RepoFix 看允许的 diff、目标与回归测试；资料研究看来源、覆盖与冲突；外部写入看 receipt。当前 `ExactTextCompletion` 仅验证固定文本。

## 三条不能混淆的边界

1. 事件记录“发生了什么”，Trace 帮助解释时间顺序，长期记忆保存获许可的用户信息；三者不能互相替代。
2. 参数 Schema 证明形状，策略判断是否允许，沙箱限制实际能力；任一层都不能单独当安全保证。
3. 本地事件事务不等于外部动作原子提交。若外部写入已经发生但 receipt 未记录，状态应先进入待对账，不盲重试，也不宣称“恰好一次”。

## 扩展原则

先保持一条可读、可测试的主链路。新模型、新任务配置和新入口在边缘接入；只有重复出现的需求才沉入 Core。第二个非代码任务若仍迫使 Runner 加 RepoFix 分支，就是架构抽象失败。此决定见 [ADR-0001](./ADR/0001-通用内核与垂直场景.md)。
