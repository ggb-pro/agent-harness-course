# Agent 工程面经：问题、参考答案与 TraceForge 拷问

> 2026-09-15 版。面向 Agent/Coding Agent 中高级岗位。题目按公开应聘者面经中反复出现的主题去重，并用 GitHub 上可核验的开源实现更新答案；**公司面经是个人自述，不是公司官方题库**。每题中的「TraceForge」状态依据本仓库 `main@5a2a51d` 的课程代码和 v0.2 原设计核对：**已实现、待实现、不能声称已实现**必须分开。配套设计见[TraceForge 项目设计文档](../学习文档/TraceForge-Agent-Harness-项目设计文档.md)。

## 如何回答

面试时先用一句话给结论，再讲控制流/失败窗口/验证指标，最后拿出自己写的代码、测试或 Trace。没有数据就说没有，不把预期提升说成实测。本文 48 道题不是背诵模板；方括号中的 S 编号对应末尾 GitHub 来源。

## A. Agent 与 Harness 核心链路

### Q01. Agent、Workflow、Harness 各是什么？
**答**：Workflow 的控制流由代码预先定义；Agent 在有限动作集合里让模型根据观察选择下一步；Harness 则负责上下文、模型调用、Tool 调度、权限、状态、预算、恢复和观测。选择依据是步骤是否稳定、风险是否可接受、环境反馈是否会改变下一步，而不是名字是否“智能”。[S1][S2]
**深入回答**：在生产系统中这三者可以嵌套：外层 Workflow 固定“澄清→检索→修改→验证”的阶段，阶段内部由 Agent 选择文件和修复方式，Harness 在所有阶段维持同一权限与状态契约。面试官若追问“为什么不全用 Agent”，回答应指向可重复性、成本和风险：确定性步骤交给代码可减少无意义推理与路径震荡；是否值得开放模型决策要用同题配对评测证明。
**TraceForge 拷问**：课程 `AgentRunner` 已有模型/工具循环；RepoFix 外层确定性流程尚未实现。不能说已有完整 Workflow/Profile。

### Q02. 从零设计一次 Agent Loop，状态怎样流转？
**答**：加载带 revision 的 RunState，检查预算/取消；构造上下文，记录请求，调用模型；解析并验证 Action；副作用前落意图并过策略；执行后记录观察，交 Verifier 判断成功或继续。每步有 `run_id/step_id/tool_call_id` 与明确终态。模型返回 `Finish` 只是候选完成，不是验收结论。[S2][S3]
**深入回答**：必须明确每个状态转移的提交点。模型请求超时与“模型已生成但客户端没收到”是不同失败；Tool 调用记录与外部副作用之间也有不确定窗口。RunState 保存累计预算、待审批调用和上次已确认观察，恢复时不能重新计费或重放已发生的写操作。接口设计应把模型、Tool、时钟与 ID 生成器抽象出来，FakeProvider 才能覆盖边界而不依赖真实模型。
**TraceForge 拷问**：现有 Runner 见无 ToolCall 就直接 `run.completed`，没有 Verifier、预算或取消；v0.3 将此列为首要补强。

### Q03. ReAct、Plan-Execute、固定 Workflow 怎么选？
**答**：可枚举且可验证的业务步骤用 Workflow；需要依环境观察持续决策时用短 ReAct 循环；长任务用显式计划，但只有证据变化或失败阈值触发重规划。用相同任务集比较成功率、调用轮次、P95、成本与安全失败率，别凭感觉选。[S1]
**深入回答**：Plan-Execute 的计划是可修订假设，不是保证正确的执行脚本；每步要写预期产物和验收条件。ReAct 容易在局部探索中取得新证据，也容易反复调用同一 Tool。对于 RepoFix，可固定工作区冻结与最终测试，允许模型在“定位与补丁候选”中迭代；若每次失败都重做整份计划，额外 token 和副作用风险会迅速增长。
**TraceForge 拷问**：RepoFix 设为外层固定阶段，定位与修复方案用模型决策；当前仓库还没有 RepoFix 运行代码。

### Q04. 如何防止 Agent 无限循环或路径震荡？
**答**：硬上限包括步数、deadline、token 与费用。对目标、规范化动作、参数、关键观察计算指纹，识别相同动作、`A→B→A` 和连续无新证据；已知错误用确定性恢复表，未知语义问题才让模型提出有界候选。停止时给出失败证据，而不是生成虚假答案。
**深入回答**：指纹不能只比较 Tool 名称，否则两次读取不同文件会误判为循环；也不能直接 hash 全部输出，否则时间戳变化掩盖重复。应抽取任务阶段、文件/资源、规范化参数和“是否得到新证据”。连续失败后给模型的不是原样历史，而是失败动作表与禁止重复的约束。指标至少包括无进展轮次、重复 Tool 比率、任务成功率及误熔断率。
**TraceForge 拷问**：当前仅有 `max_turns`；还缺指纹、预算账本与进展检查。

### Q05. 模型返回多个并行 ToolCall 时怎么处理？
**答**：先检查每个动作的权限、读写集与依赖。独立只读动作可有界并发；共享文件写、审批和有副作用动作需串行或隔离工作区。所有子任务继承取消/deadline，结果以调用 ID 配对，失败不得悄悄吞掉。并行收益要扣除冲突与聚合成本。[S3]
**深入回答**：调度器先根据规范化资源键建立冲突图，再按并发上限执行；并行返回顺序不等于模型请求顺序，必须保留稳定 call ID，给模型的观察也要能复原因果。一个调用失败时要定义是否取消同批兄弟任务，以及已启动写操作如何对账。比较串行与并行的关键路径 P95、冲突率和质量，而不只比较平均耗时。
**TraceForge 拷问**：现有 Runner 顺序执行 ToolCall；并行是扩展，不应把顺序实现描述为并发框架。

### Q06. Multi-Agent 什么时候比单 Agent 好？
**答**：任务可独立验收、可并行、需要权限或上下文隔离时才拆分。先测单 Agent 基线，计算额外模型轮次、通信成本和冲突率；主 Agent 对结果复核与最终提交负责。多个 Agent 同时写同一 checkout 是高风险设计。[S1][S4]
**深入回答**：拆分粒度应围绕可交付接口而非“一个步骤一个 Agent”。Explore 可以只读查证并返回文件位置和不确定性，主控再验证；修复 Agent 若需要写入，则各用隔离 worktree。还要决定失败传播：子任务超时是否允许部分结果、其发现是否过期、它是否获得与父任务相同的凭据。没有单 Agent 对照数据时，多 Agent 只是复杂度增加。
**TraceForge 拷问**：Explore Subagent 当前仅在设计里；目标是只读隔离 worktree，输出带文件引用的结构化发现。

### Q07. Manager-as-tool 与 handoff 有何区别？
**答**：Manager-as-tool 保留主控和最终汇总；handoff 把后续对话控制权转给专职 Agent。两者都要限定可见历史和权限，转交本身也要被审计；不能假定普通 Tool guardrail 自动覆盖 handoff。[S4]
**深入回答**：两种模式最关键的差别是“谁对最终输出和后续 Tool 调用负责”。Manager 模式可对下游结果加统一验收；handoff 模式需明确接收者是否继承预算、审批与历史，以及如何返回原 Agent。切换时不能把低信任摘要当作新的系统指令。故障测试要覆盖移交后崩溃、重复移交和子 Agent 请求高权限 Tool。
**TraceForge 拷问**：v1 先用主控调用只读 Explore，暂不做任意 Agent 间 handoff。

### Q08. 如何判断 Agent 已完成用户任务？
**答**：使用外部可验证的验收器：文件改动范围、测试退出码、期望行为、约束遵守和证据引用。模型文本是建议，不能作为唯一成功信号。若测试不可运行，应输出 `UNVERIFIED` 和原因，不可声称已修复。
**深入回答**：验收器应先定义任务级成功，再定义可机器验证的代理指标。测试通过仍可能是补丁无关、覆盖不足或隐藏测试失败，因此需核对 diff 与目标故障，并保留未覆盖风险；反过来，测试环境损坏不能简单归责模型。面试官问“成功率”时，应给出样本定义、判定脚本、失败分桶和人工复核比例。
**TraceForge 拷问**：当前 Runner 无验证器；这是 v0.2 最关键的“完成即成功”漏洞。

## B. Context、Memory 与检索

### Q09. 对话历史、执行状态、长期 Memory 为什么分开？
**答**：历史是可回溯证据；RunState 保存预算、待审批动作和未完成步骤等权威状态；长期 Memory 是跨任务、可纠错和过期的候选知识。摘要仅是模型输入视图，不能替代执行状态。[S5]
**深入回答**：这三层的生命周期和授权域不同：历史可大量追加，RunState 必须强一致并可恢复，Memory 需要来源、TTL 和用户纠错。若把“用户禁止写配置”只放在摘要里，压缩丢失就会造成越权；若把一次 Tool 失败写成长期记忆，下个任务会被污染。设计存储接口时应分别定义所有者、更新规则和删除语义。
**TraceForge 拷问**：当前消息数组只在 Runner 内存；尚无持久化 RunState 或长期 Memory。

### Q10. Context 压缩怎样保证不丢需求？
**答**：把用户目标、否定条件、权限、关键实体/数值、待完成事项和证据引用存为 `protected_state`。只摘要可回取的旧观察和重复推理，摘要记录原事件 ID；压缩前后做结构化约束 diff，不一致即回滚。评测约束保留率、成功率、压缩率和成本。
**深入回答**：摘要器不应自行判断哪些权限“已经不重要”；由代码先锁定 protected state，再在剩余预算内选择内容。摘要需标记原文范围、生成模型与版本、损失风险，关键事实可按引用回取。测试要专门构造否定词、路径、金额、版本号和互相冲突的旧指令，比较压缩前后的动作正确率；必保留项超预算时明确停机，而不是继续截断。
**TraceForge 拷问**：独立 `ContextBuilder` 尚未接入 Runner；现有 `required` 项甚至可超预算返回，目标是明确停止。

### Q11. Tool 结果巨大，怎样放进上下文？
**答**：结果保留结构化状态、关键证据、截断标记和可回取句柄；按问题需要分段读取。不要让模型仅凭截断摘要做无法验证的结论，也不要直接把全部日志塞进窗口。量化证据遗漏率、token 成本和任务成功率。
**深入回答**：Tool 应先在可信代码中限定最大响应体，再给模型“摘要 + 命中行 + 原文句柄”，原始大结果放在受权限控制的制品存储。截断时必须明确原文是否完整，错误堆栈和测试失败信息要保留关键上下文。对比实验要同时观察是否丢掉真正失败行、是否增加二次读取次数，以及模型对“未见部分”的错误推断率。
**TraceForge 拷问**：当前 Runner 把 ToolResult.value 直接塞进 messages，没有尺寸限制。

### Q12. 如何治理几百个 Tool？
**答**：先按权限、场景和版本过滤，再召回 Top-K 候选；描述中写清适用与不适用案例，参数用 Schema 验证。评测 Tool Recall@K、Top-1、参数一次通过率与冗余调用率，不能只看最终回答。
**深入回答**：Tool 检索绝不能越过权限过滤：一个高相关但无权调用的工具不应进入候选。别名、版本和相近职责需要统一身份与互斥描述，否则模型会在 `search_file` 与 `grep_repo` 之间震荡。Top-K 太小会漏工具，太大又抬高 prompt 成本；按任务类别画召回—延迟—费用曲线，并对危险 Tool 采用显式绑定而非语义召回。
**TraceForge 拷问**：当前 Registry 仅保存名称和 handler，连 Schema 与版本都没有。

### Q13. Prompt Cache 如何设计且不泄露用户数据？
**答**：缓存稳定的系统前缀、版本化 Tool Schema 与公共规则；缓存键包含模型/推理配置、模板、工具集和权限域。用户 Memory、仓库私有内容和实时数据不能跨权限域复用；版本变化要失效。看命中率、TTFT、费用和错误复用率。
**深入回答**：先区分供应商前缀缓存、应用侧精确缓存和语义缓存，它们的失效条件不同。对编码任务，工作区 SHA、权限与 Tool Schema 变化会使旧前缀可能产生错误行为；即使命中缓存也必须重新执行实时策略。把缓存命中率与延迟、输入 token、权限隔离事故一起看，不能为了提高命中率把私有仓库内容放入跨用户共享前缀。
**TraceForge 拷问**：尚未实现缓存；先做好 Prompt 来源与权限隔离，不应为了命中率破坏边界。

### Q14. 长期 Memory 如何提取、纠错与遗忘？
**答**：候选记忆需来源、时间、主体、置信度和适用范围；写入前去重，读取时带权限与 TTL，冲突时保留来源并允许用户更正/删除。低信任检索内容不能变成系统指令。先证明真实任务有收益再引入存储。[S5]
**深入回答**：记忆写入要分事实、偏好与临时任务状态；事实更新应保留旧值的来源和生效时间，偏好应可由用户纠正，临时状态不应无限期跨任务传播。检索时先做主体与租户隔离，再按相关性和时效排序，并在模型输入中标注“候选记忆”。评测既要看召回收益，也要看错误记忆导致的任务失败和删除后是否仍被引用。
**TraceForge 拷问**：v0.3 非目标，不得写进当前功能或简历。

### Q15. Query Rewrite 如何避免偏离用户意图？
**答**：输出改写文本、保留约束、新增词与置信度；低置信时原查询和改写查询双路检索，关键歧义请用户澄清。评估 Recall@K、MRR、约束保留率和语义漂移率。
**深入回答**：Rewrite 可分指代消解、实体标准化、同义扩展和问题拆分；它们的错误成本不同。模型新增条件必须显式标记，不能把推测写成用户原意。线上落地通常保留原 Query 作对照检索，比较新旧结果的交集和额外证据，再把最终答案中的每条引用回溯到原 Query 或改写路径，以便定位误召回。
**TraceForge 拷问**：RepoFix 的代码搜索可先用原始关键词与符号引用，复杂 Rewrite 不是 MVP 必需。

### Q16. RAG 的 Recall@K、Faithfulness 分别如何算？
**答**：Recall@K 需要标注相关证据集合，算 Top-K 命中的相关项比例；没有标注不能宣称具体 Recall。Faithfulness 检查答案每个事实是否被检索证据支持，可用人工抽检与校准过的 Judge 辅助，关键事实保留引用。检索是 Agent 的证据工具，不自动保证答案正确。
**深入回答**：先固定“相关”的粒度：文档、段落还是事实；否则 Recall@K 数字不可比较。Faithfulness 与答案正确性也不同：引用支持的旧资料仍可能过时。评测应分检索漏召、排序失误、证据冲突、生成幻觉和应拒答未拒答；每层对应不同修复策略。无标注数据时可做人工抽样或弱标签实验，但必须如实称代理指标。
**TraceForge 拷问**：本项目首要评测是 RepoFix 行为，RAG 留给后续 KnowledgeAudit Profile。

## C. Tool、权限、安全与协议

### Q17. 生产 Tool 契约应包含什么？
**答**：`name/version`、用途和反例、输入/输出 Schema、权限、风险、超时、输出上限、错误码、幂等与对账能力。ToolCall 先解析和 Schema 校验，再经业务/权限检查，最后执行。Schema 约束格式，不代表授权。[S3]
**深入回答**：Tool 契约还要写明执行语义：读是否稳定、写是否可逆、超时后结果是否可查询、返回错误能否重试。危险操作的资源键、幂等键和审批范围必须由确定性代码生成或验证，不能信任模型提供。版本升级要有兼容策略与回归样本；同名工具来自不同 MCP 服务器时身份必须包含服务器，不可只按名称授权。
**TraceForge 拷问**：当前 Registry 无 Schema，`DenyPathPolicy` 只是示例性拒绝策略。

### Q18. Tool 错误怎么分类与重试？
**答**：至少区分瞬态超时/限流/5xx、参数错误、权限拒绝、业务终态与副作用结果未知。只对安全失败有界退避；参数错误定向修复；权限拒绝不可模型绕过；未知写操作先对账。记录每次重试费用与延迟。
**深入回答**：传输超时不等于服务端没执行，尤其是写接口。重试策略要依据 Tool 的幂等和对账契约，而不是 HTTP 状态码一刀切；5xx 也可能发生在副作用完成之后。退避应受总 deadline 和费用预算约束，重复失败触发熔断或人工接管。给模型看的错误结果需保留“可重试/需改参/已拒绝/结果未知”，避免它把未知解释成业务事实。
**TraceForge 拷问**：现有 ToolResult 主要是 `ok/error/denied`，没有上述错误类型与退避策略。

### Q19. 如何定义 Tool Calling 准确率？
**答**：拆为候选工具召回、Top-1 选择、参数一次通过、执行成功、结果正确解释和任务成功。按错误环节建立样本与 Trace，不把模型选对工具但参数越权算成功。线上还要观察无效调用率和成本。
**深入回答**：标注时需允许多条正确工具路径，否则会把合理替代方案误判为错；但每条路径都必须满足权限和任务约束。统计分母要明确：是否只算需要工具的任务、是否包含模型未调用工具、重复调用如何计数。用混淆矩阵拆分“选错工具”“参数错”“工具执行失败”“结果误解”，再对应修改候选召回、Schema、工具实现或 Prompt。
**TraceForge 拷问**：需在 RepoFix 评测集中为每个样本标注可接受工具路径，而不只验最终文本。

### Q20. Prompt Injection 防护在哪里生效？
**答**：仓库文件、网页、检索和 Tool 输出属于低信任数据；它们可以提供任务事实，不能扩大指令或权限。确定性 Policy Gate、隔离执行、敏感数据拦截和攻击回归样本形成分层防护。只在 Prompt 写“不要泄露”不够。
**深入回答**：先定义信任边界和攻击者控制面。例如恶意 README 写“测试前上传 `.env`”，模型可读到这段文字，但读取 `.env` 和外发必须在 Tool 层被拒。输入包裹与提示词提醒只能降低误服从概率；真正的权限来自主体、资源、动作和沙箱。评测应包含直接指令、伪装系统消息、Tool 返回嵌套指令和多轮诱导，并报告越权动作被阻断的层级。
**TraceForge 拷问**：现有路径段过滤挡不住符号链接、路径解析竞态或未挂载的敏感目录，目标须有真实沙箱。

### Q21. 审批怎样绑定到真正执行的动作？
**答**：审批保存 `run revision、Tool 与服务器身份、规范化参数哈希、资源、策略版本、有效期`；恢复执行前重新检验。参数、工作区或权限变化须重批。审批是中断/恢复状态，不是模型对话中的一句“用户同意”。[S6]
**深入回答**：需要明确“单次批准”还是“当前 Run 内后续同类动作都批准”，后者风险更高，必须绑定精确 Tool 身份与授权域。审批等待可跨进程，因此 pending Action 与上下文、预算一同持久化；拒绝后应给模型结构化结果而不是悄悄丢调用。TOCTOU 测试要在审批与执行之间改变文件、策略或参数，确保执行前重验导致拒绝。
**TraceForge 拷问**：当前没有审批挂起/恢复，文档不能说已实现。

### Q22. Sandbox 的边界是什么？
**答**：工作目录、挂载、进程、网络、CPU/内存、时间和凭据都应显式受控；启动失败则停止，不回退宿主机。执行参数用结构化 argv，真实路径检查与 Tool 权限检查仍需保留。沙箱是能力边界，不能替代审计和审批。
**深入回答**：对 Coding Agent，沙箱至少要隔离工作区与宿主凭据、限制网络外联、管控子进程和输出体积。文件名检查需考虑符号链接与路径规范化，命令执行需防环境变量泄漏和进程树残留。验收不只跑一次正常命令，还要故意访问仓库外、启动长寿命子进程、耗尽内存和在沙箱启动失败时确认没有宿主机回退。
**TraceForge 拷问**：当前课程代码没有沙箱；RepoFix 上线前必须实现。

### Q23. MCP 是 Tool Registry 的替代品吗？
**答**：MCP 定义外部工具、资源和提示的交互协议；Harness 仍负责可信服务器选择、候选 Tool 暴露、输入校验、权限、审计和成本。远程授权须校验 token audience，禁止把收到的 token 原样透传下游。[S7]
**深入回答**：MCP server 可能动态增加工具或更新描述，连接阶段就要锁定来源、版本与可见能力，运行时再按用户和任务收紧权限。同名工具来自不同 server 必须有不同身份；返回的资源和提示仍是低信任内容。远程服务的 token 必须面向该服务本身，下游 API 使用单独凭据。评测不能只测“能连上”，还要测越权工具发现、参数注入和连接中断恢复。
**TraceForge 拷问**：MCP 是 v0.3 之后的适配器，不能先接协议再补安全边界。

### Q24. Skill 与普通 Prompt 文件的区别？
**答**：可发布 Skill 应有版本、Owner、依赖、权限、适用场景、回归集与回滚路径；按需加载后仍受 Tool 权限约束。若只是几段提示词，不应称为可治理的 SkillHub。评测选择准确率、任务收益、越权率与成本。
**深入回答**：Skill 通过文本影响模型决策，不能成为额外授权主体。发布流水线至少检查来源与许可证、依赖的 Tool/权限、提示注入样本和目标任务回归；运行时固定版本并记录在 Trace 中。灰度中若出现成功率下降或新越权请求，应支持禁用单个 Skill，而不是整个平台回滚。只有当可发现、可评测、可撤销时才值得做 SkillHub。
**TraceForge 拷问**：当前 Profile 是设计，SkillHub 尚不存在；先实现稳定内核。

## D. 状态、恢复、并发与观测

### Q25. Event Log、Checkpoint、Trace、日志如何分工？
**答**：Event Log 是业务状态事实；Checkpoint 是由事件导出的恢复加速；Trace 解释调用因果与耗时；普通日志用于节点诊断。它们通过 run/step ID 关联，但不能把 Trace 当数据库，也不能用日志反推可靠状态。[S2][S8]
**深入回答**：Event 的设计从恢复不变量出发：审批是否有效、Effect 是否已开始、预算是否已扣、终态是否已提交；Trace 则可以采样或脱敏，不适合作这些权威事实。Checkpoint 需标明覆盖到哪个事件序号和 schema 版本，重启时校验后增量重放。若模型请求使用了某个 Prompt 版本但日志没保存来源，事后“重放”最多还原界面，无法解释决策。[DSH Session](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md)
**TraceForge 拷问**：课程只有 JSONL Event Store 和简单 Projection，缺 Snapshot、完整性校验及 Trace span。

### Q26. 离线 Replay 是否能重现模型思考？
**答**：不能保证。离线 replay 应重建已记录事件、状态和策略判断，不重新执行外部副作用；重新请求模型是另一种实验，可能因模型版本和采样变化得到不同轨迹。必须记录 Prompt、工具和代码版本以解释差异。[S2]
**深入回答**：至少区分三种回放：事件投影重建、以录制模型/工具输出执行的确定性回归、真实模型重新运行。第一种验证存储与投影，第二种验证 Harness 控制流，第三种验证模型行为统计；三者结果不可混称。外部 Tool 的副作用在前两种回放中必须被 mock 或读取 receipt，不能再次执行。报告时注明模型版本、Prompt 哈希、工具 Schema、仓库 SHA 和随机种子。
**TraceForge 拷问**：当前 `project_run` 是简单事件投影，CLI `replay --offline` 仍是草案。

### Q27. Tool 成功后、Journal 写成功前崩溃怎么办？
**答**：先持久化执行意图，外部调用使用稳定幂等键；恢复时若状态为 `started/unknown`，查询外部 receipt 或对账，不能直接再执行。无对账能力且可能不可逆时停在待人工处理。跨系统不笼统承诺“恰好一次”。
**深入回答**：最困难的是外部系统“成功提交、返回包丢失”的窗口。若外部 API 接受幂等键且可查询结果，恢复可复用同一键或读取 receipt；若是没有查询能力的命令或第三方写接口，只能把状态列为不确定并由人工判断。补偿动作也不是无代价回滚，必须是新的、有权限和审计的副作用。故障注入需在意图写前后、外部调用前后、结果落盘前后逐点杀进程。
**TraceForge 拷问**：当前 `EffectJournal` 是内存字典，崩溃后丢失；v0.2“第三天验证不重复”必须降为进程内验证。

### Q28. JSONL Event Store 有哪些恢复风险？
**答**：末行部分写入、并发 writer、重复序号、写入未 fsync、schema 迁移和文件损坏都可能改变投影。单机阶段至少一个 writer、尾部检测、校验和与备份；需要事件与意图事务提交时转 SQLite/Postgres。
**深入回答**：当前按 `len(load(run_id))+1` 算序号在两个进程同时写时会撞号；追加系统调用成功也不等于断电后持久。JSONL 适合教学和单 writer 原型，恢复时需识别截断末行，并区分“可忽略的未提交尾部”和“中间损坏”。当事件、Run revision 与 Effect 意图必须原子提交时，继续给 JSONL 打补丁比引入事务数据库更危险。
**TraceForge 拷问**：当前 `JsonlEventStore.append()` 先读全文件计算序号再追加，无并发互斥和持久化屏障。

### Q29. 异步慢 Tool 如何挂起与恢复？
**答**：提交任务后落 `WAITING_TOOL`，worker 以租约执行；先持久化结果，再 ACK/回调；编排器用 revision/CAS 去重消费。取消和迟到结果按持久化顺序裁决，超时不代表 Tool 没执行。
**深入回答**：租约只是把任务交给某个 worker 的暂时所有权，租约过期后旧 worker 仍可能完成，因此要有 fencing token 或结果版本检查。结果保存与消息 ACK 顺序反了会丢结果；重复投递是正常情况，消费者必须幂等。Agent 恢复时先判断工具是否完成、运行中还是未知，而不是盲目重新调用模型。衡量排队 P95、恢复耗时、重复执行率和未知结果积压。
**TraceForge 拷问**：当前同步工具运行时；异步是后续阶段，需先打牢 Effect 语义。

### Q30. 多 Agent 并发写一个仓库怎么办？
**答**：每个子 Agent 用基于同一 SHA 的隔离 worktree，产出补丁；主控检测写集和基线差异，再合并、回归，冲突时重评估或人工处理。共享 RunState 用 CAS，不能最后写入者获胜。
**深入回答**：文件名不冲突不代表语义不冲突：两个补丁可能分别改函数签名和调用方，也可能同时更新同一依赖版本。合并后必须重新运行相关测试与静态检查，且主控保留每个子 Agent 的来源和权限记录。对代码修复，先用只读 Explore 子任务取得并行收益，再逐步开放写能力；以单 Agent 基线评估是否值得承受合并成本。
**TraceForge 拷问**：v1 Explore 只读，避免过早承受写冲突。

### Q31. 如何传播取消与 deadline？
**答**：父 Run 的 deadline 传给模型、Tool、worker 与子任务；进程组清理并在日志里记录取消原因。若取消与外部动作成功竞态，不能假定成功被撤销，要照样对账和报告。
**深入回答**：取消是“停止继续推进”的请求，不是时光倒流。Provider 可能收到取消后仍返回结果；Tool 进程可能在被终止前已写文件；消息队列里的任务可能已被 worker 领取。协议要明确哪个事件先提交、后到结果如何归档、是否允许恢复，以及预算如何结算。测试应覆盖取消在模型流式响应、Tool 执行中和审批等待时分别发生。
**TraceForge 拷问**：当前 Provider.complete 未接 context/cancellation，后续接口需要改造。

### Q32. Token 与 P95 突增怎么定位？
**答**：按模型请求、上下文构造、Tool 排队/执行、重试、压缩和子任务拆分 Trace 与 usage。检查调用轮次、Tool 结果体积、缓存命中、模型版本、提示模板和循环情况；优化后同时看成功率，避免只降成本。[S8]
**深入回答**：单位任务成本不是“单次模型价格”，而是每类调用数乘输入/输出 token，加上压缩、重试和子 Agent 的总账。延迟要看关键路径：并行 Tool 总时间不应简单相加。先按任务类型和版本分桶，再检查某次发布是否造成工具结果膨胀、循环增多或 Prompt Cache 失效；对照质量、安全、P95/P99 和费用，防止便宜模型造成更多失败重试。
**TraceForge 拷问**：课程尚无 usage ledger；文档应将未知 token 记为未知，不能记 0。

### Q33. Redis 锁或 MQ 能保证恰好一次吗？
**答**：不能。锁可能过期或失去所有权，消息通常至少一次投递；用 fencing token/状态版本、下游幂等键和结果对账。结果应先持久化再 ACK，重复回调 CAS 去重。
**深入回答**：Redis 锁减少并发进入，但进程暂停后锁可能已经转给新 worker，旧 worker 恢复仍会写下游；只有下游识别更高的 fencing token 才能拒绝旧持有者。MQ 消费者在处理完成、ACK 前崩溃会收到重复消息，这是预期行为。面试时应主动区分“最多一次、至少一次、最终业务效果幂等”，不要把消息投递语义误说成外部副作用恰好一次。
**TraceForge 拷问**：先做单进程持久化与故障注入，再谈分布式 worker。

## E. 评测、发布与项目深挖

### Q34. 一个合格的 Agent 评测集如何构造？
**答**：分任务类型、难度、失败模式和风险；真实脱敏 Bad Case、合成边界和攻击样本分开标记。固定输入、仓库 SHA、环境、预期结果与判定脚本，开发集与留出集分离；报告分桶而不只给总分。
**深入回答**：题库要覆盖正常修复、模糊需求、环境故障、权限诱导、长上下文与崩溃点；每个样本写清允许的多种正确路径、禁止动作和独立验收器。真实模型存在方差，应多次运行并报告区间，而 FakeProvider 负责结构性不变量回归。Bad Case 进入开发集后，留出集必须保持独立；否则一次次“补丁式调 Prompt”会把模型过拟合到公开题。
**TraceForge 拷问**：原设计说“初始 20 题”，仓库目前没有题集，属于目标而非成果。

### Q35. Agent 成功率如何定义？
**答**：以外部可验证的任务验收为主，同时报告约束遵守、测试通过、重复副作用、安全违规、P95 和费用。LLM Judge 可以辅助主观质量，但需要人工标注校准；不能让模型自报任务成功。
**深入回答**：先定义分母：所有提交任务、仅可运行任务还是排除环境故障；不同口径会显著改变成功率。代码修复的成功可要求补丁可应用、目标测试与相关回归通过、未越权修改和最终说明有证据。安全违规与重复外部写应单列硬门禁，不能被平均成功率稀释。Judge 适合说明质量等主观项，但要校准偏差与复核分歧样本。
**TraceForge 拷问**：RepoFix Verifier 必须检查补丁、测试、路径和证据，缺一不标完成。

### Q36. 修一个 Bad Case 怎么证明没伤别的 Case？
**答**：最小复现进入回归集，旧新版本在同样任务、模型版本和环境下配对运行；比较分桶成功率、延迟、成本和安全门禁，保留失败样本。样本量不足时明确置信限制。
**深入回答**：先判断根因位于模型选择、Tool 参数、执行、状态、证据消费还是验收，不要为一个失败到处改 Prompt。修复后在同一仓库 SHA 和环境下跑新增样本、同类样本以及完整留出集；对非确定性模型报告重复运行和置信区间。若修复提高了目标 Case，却增加越权尝试或 P95，不能宣称整体提升；记录权衡和回滚条件。
**TraceForge 拷问**：FakeProvider 的结构回归与真实模型任务成功率是两层测试，不能混成一项。

### Q37. Shadow、Canary、A/B 分别用于什么？
**答**：Shadow 在真实请求旁路运行且不执行副作用，用于比较动作与风险；Canary 小比例真实执行，观察系统指标；A/B 对照用户结果。每一步需停机与回滚条件，离线通过不等于可上线。
**深入回答**：Shadow 的模型决策可能受“不能执行写操作”影响，因此它适合发现候选动作和分布漂移，不能完全替代真实任务验收。Canary 应按用户/任务稳定分流，控制版本、流量和风险，并有 kill switch；A/B 还要考虑学习效应与任务难度差异。高风险权限和重复副作用属于发布前阻断项，不能等到线上统计显著才处理。
**TraceForge 拷问**：个人项目当前无线上流量，不能虚构 Canary 结果；可只做离线回归。

### Q38. 如何做模型路由与小模型升级？
**答**：按任务复杂度、风险和可验证性路由；简单可验收步骤先走成本低的模型，失败或低置信升级。比较端到端质量、升级率、P95、总 token 与费用，而不是单看模型单价。
**深入回答**：路由规则先用确定性特征（任务长度、工具需求、风险级别、历史失败类型）建立基线，模型预测复杂度可作为后续增量。升级触发必须区分“真难题”与“工具故障”，否则大模型只会更贵地重复坏调用。统计要把初次请求、升级请求和失败重试都算入一项任务，防止小模型看似便宜但总成本更高。
**TraceForge 拷问**：先有评测与 usage ledger，后做路由；目前只有 FakeProvider。

### Q39. 什么情况下 LLM 自动诊断故障？
**答**：超时、限流、权限、参数错误等先由代码分类；未知语义失败可请模型给出结构化根因候选与证据。恢复动作仍走白名单、权限、预算、风险校验，高风险转人工。测根因命中率、误恢复率与额外费用。
**深入回答**：诊断 Agent 只应读脱敏 Trace、状态版本和错误证据，返回“候选根因—证据—推荐动作—不确定性”，不能直接拿到无限写权限。恢复器由确定性代码判断动作是否合法，并限制最大尝试次数。对账是写操作结果未知时的前置条件；若模型误把“未收到响应”诊断成“未执行”，会造成重复副作用。评测需刻意放入错误码相同、根因不同的样本。
**TraceForge 拷问**：不要把 LLM 诊断放在 Effect 对账前，避免“修复”造成重复副作用。

### Q40. 如何证明项目不是套壳？
**答**：列明复用的模型接口/协议和自己写的状态机、Policy、持久化、对账、验收与评测；展示失败案例、设计取舍、代码位置和测试证据。项目叙述区分“已运行课程原型”和“目标生产能力”。
**深入回答**：优秀回答不是强调“全部自研”，而是说清为何某些组件复用、自己对哪条不变量负责。例如用现成 Provider SDK，但自己实现审批动作绑定、Effect 对账和故障注入；展示一次真实 crash case 从症状到修复和回归。面试官问“你改了什么、为什么不用 LangGraph/Agents SDK”时，必须能拿同题基线和工程取舍回答，而不是贬低框架。
**TraceForge 拷问**：当前可展示 21 项测试与课程链路，但不能写跨进程恢复、沙箱或 RepoFix 成功率。

### Q41. 没有真实线上流量怎样证明工程深度？
**答**：公布固定基准、故障注入、攻击样本、运行脚本、代码覆盖关键边界和失败复盘。说明它证明的是可复现的工程性质，不是生产规模或商业收益。
**深入回答**：个人项目可提供 `make eval` 或等价脚本，固定仓库 SHA、模型版本、测试种子与环境，并展示成功和失败两类轨迹。关键证据包括跨进程 crash matrix、越权阻断样本、重复 Tool 去重、P95 与费用分布。若只展示一次“模型修好了代码”，那是演示而非系统性评测；如果没有真实线上数据，应主动说明局限。
**TraceForge 拷问**：用 crash matrix 与 event/Effect 不变量作为作品集证据，比不真实的“提升 X%”更可信。

### Q42. 一分钟项目介绍怎么说？
**答**：先讲问题与基线，再说自己实现的边界、最难故障与权衡、验证结果，最后讲局限和下一步。每个数都给样本、版本和运行条件。遇到尚未实现的问题坦诚说明设计与计划，不以文档代替成果。
**深入回答**：一个可用的结构是：“普通模型/Tool 循环在崩溃恢复和越权执行上不可控；我实现了 X、Y、Z；最难的是外部成功但本地未记录，所以采用意图先写与对账；在 N 个固定样本和 M 个故障点上，结果为……；当前尚无生产流量。”具体 X/Y/Z 和数字只能填真实代码与实验。被追问时顺着失败窗口展开，不背大段架构名词。
**TraceForge 拷问**：当前准确说法是“可运行的 Python 标准库教学原型 + 21 项测试 + v0.3 目标设计”。

## F. 补充现场追问

### Q43. Function Calling 参数合法就可以执行吗？
**答**：不可以。解析成功只是协议层；还要检查 Schema、业务条件、主体权限、资源边界、预算和是否需要审批。执行前再次校验状态版本，避免审批后参数或环境改变。[S3][S6]
**深入回答**：即便模型输出完全符合 JSON Schema，例如 `{path:"../../secret"}` 也可能违反工作区边界；合法路径在审批后还可能经符号链接被重定向。验证应分两阶段：提案时给出审批所见动作，执行时按当前真实状态重验。危险 Tool 的调用 ID、服务器身份和规范化参数都要进入审计，不能只靠模型生成的文本描述。
**TraceForge 拷问**：当前 ToolRegistry 甚至没有严格 Schema，需先补契约。

### Q44. 模型接口的“四层成功”是什么？
**答**：传输成功、协议可解析、语义正确、用户任务完成。HTTP 200 或 JSON 合法并不保证选对 Tool，更不保证代码修复成功。错误码和指标必须分层统计。
**深入回答**：第一层看网络/TLS/超时和供应商错误；第二层看响应是否完整、结构化参数能否解析；第三层看所选 Tool、参数及证据是否正确；第四层用外部验收器判断用户目标。每层失败的处理不同：传输可有限重试、解析需修复或降级、语义要分析模型与工具描述、任务失败需看完整链路。把四层混成“API 成功率”会掩盖真正问题。
**TraceForge 拷问**：现有 `run.completed` 只等价于收到没有 ToolCall 的响应，不代表任务成功。

### Q45. 流式响应中断了怎么处理？
**答**：不执行未完整确认的 ToolCall；保存已确认的调用 ID 和请求状态。协议支持续传则按官方语义恢复，否则重新请求，同时避免对已执行副作用重放。报告中区分模型中断与 Tool 结果未知。
**深入回答**：流式 token 只是临时显示，不能边收到半个 JSON 边执行写工具。若工具调用已完整落盘并启动，后续网络断开不应让 Runner 重新分配 call ID；应先查事件与 Journal。向用户的流式文字可能已经显示了未经验证的“已修复”，产品层要把过程状态与最终验收区分。测试覆盖断在参数中间、调用边界和结果回传后的三类位置。
**TraceForge 拷问**：当前同步 `complete()`，流式支持是后续适配器能力。

### Q46. Go 中怎样将外部并发调用限制为 3？
**答**：使用继承父 `context` 的 `errgroup.SetLimit(3)` 或信号量；为每个调用设 deadline，结果按 ID 汇集并保留部分成功。共享状态只在聚合点或 CAS 下更新，取消后清理 worker。
**深入回答**：并发上限应包住真正的外部调用，而不是仅包任务创建；使用 `errgroup` 时要明确一个任务失败是否取消其它任务。多个渠道询价等读操作可返回部分成功，但写操作不能在结果不明时重复提交。聚合结果按原请求顺序或稳定 ID 输出，防止完成顺序改变模型上下文。用压测观察并发数、队列等待 P95、超时率和下游限流。
**TraceForge 拷问**：本仓库是 Python 教学原型，不为面试叙事临时宣称 Go 实现；Go 并发题可基于既有后端经验单独回答。

### Q47. IVF 的 nlist 与 nprobe 如何权衡？
**答**：nlist 决定索引簇数，nprobe 决定查询探测簇数；更大 nprobe 通常提高召回也增加延迟。用标注集画 Recall@K-P95 曲线，并考虑索引构建和更新成本；不能凭单一默认值给结论。
**深入回答**：nlist 太小会导致每个倒排列表大、扫描多；太大则可能训练不充分或列表稀疏。nprobe 改变候选覆盖，需在相同向量、索引规模、过滤条件和硬件下测曲线。若业务还要时间/权限过滤，先后顺序会影响实际召回和延迟；不要把 ANN 的候选召回与最终 RAG 答案质量混为一谈。
**TraceForge 拷问**：这是知识检索岗位扩展题，不必强塞进 RepoFix MVP。

### Q48. 检索证据不足或互相冲突怎么办？
**答**：先核对来源、时间、实体和版本；有冲突就保留两边证据，不编造统一结论。关键事实不足时补查或明确拒答；记录证据引用，评测错误接受率与不必要拒答率。
**深入回答**：冲突可来自同一实体不同时间、不同版本文档、低质量转载或检索误匹配；归因不同，处理也不同。先让系统标出矛盾字段和来源，而不是直接让模型“综合一下”；关键决策需要再检索权威来源或请用户确认。回答应说明哪些结论有证据、哪些是推断、哪些仍未确定，并把冲突样本纳入回归集。
**TraceForge 拷问**：RepoFix 可类比为测试与代码证据冲突，Verifier 应给 `UNVERIFIED`，不能采纳模型自述。

## 两道系统设计长答示范

### 示范一：设计一个可恢复、可审计的写 Tool

**面试问题**：“Agent 自动修改仓库文件，进程崩溃或工具超时后如何保证不会重复写？”

**先给结论**：我不会笼统承诺“恰好一次”。我会把模型提案、授权、意图、外部执行、结果确认分成独立状态，并把“不知道是否执行成功”保留为明确状态。安全性来自稳定动作身份、持久化意图、对账和真实工作区隔离，而不是重试次数设为零。

**展开协议**：模型提交 `apply_patch` 及参数后，Harness 先做 Schema、允许路径、真实路径、预算和权限检查；需要审批时保存原动作哈希及 run revision。执行前在本地事务中写入 `effect_id、动作哈希、幂等键、STARTED`。工具在基于固定仓库 SHA 的隔离 worktree 中执行，保留补丁哈希、文件前后哈希及退出状态；结果落盘后才通知 Runner 继续。若崩溃发生在调用之后、结果落盘之前，恢复时先查工作区及外部 receipt，确认已执行则补记结果；确认未执行才允许原键重试；无法确认则停在 `NEEDS_RECONCILIATION`，由人工处理。审批不能沿用到参数或仓库状态已改变的动作。

**失败与验证**：故障注入覆盖意图提交前后、文件写入前后、结果记录前后、事件通知前后；每个点都检查事件序列、文件哈希、预算、重复写入与最终状态。对比单纯进程内字典缓存，跨进程崩溃后能否识别 `UNKNOWN` 是关键差异。当前 TraceForge 课程代码仅能在同一进程复用结果，[设计文档](../学习文档/TraceForge-Agent-Harness-项目设计文档.md)中的跨进程协议还是待实现目标，这句话在面试时必须主动说清。

### 示范二：如何证明 Harness 改动真的提高任务质量

**面试问题**：“你把 Context 压缩和 Tool 路由改了，如何证明不是只修好几个样例？”

**先给结论**：我会先冻结任务和判定规则，再用配对实验比较旧新版本，并分层报告成功率、安全、延迟和成本。单条好看的 Trace 是调试证据，不是总体收益；模型有波动时需要重复运行与置信区间。

**展开实验**：评测集分基础修复、长上下文、工具歧义、权限诱导、超时/崩溃、证据冲突。每题固定仓库 SHA、用户约束、允许修改范围、测试脚本和多种可接受路径。Context 改动重点看约束保留率、压缩率与最终任务成功；Tool 路由重点看候选 Recall@K、Top-1、参数一次通过率和冗余调用。新旧版本用同一模型版本、采样配置和环境，按任务配对运行；开发集用来调试，留出集不参与调 Prompt。先用 FakeProvider 做确定性结构回归，再用真实模型做多次端到端实验。

**决策与发布**：安全违规和重复副作用是硬阻断；任务成功率提升若伴随 P95 或费用不可接受，也不能直接发布。逐项报告失败分桶、样本数、重复次数和不确定性，并保存 Bad Case 的输入、版本、Trace、修复与新增回归。个人项目没有生产流量时只报告离线结果，不能虚构 Shadow 或 Canary。TraceForge 仓库目前有 21 项课程测试，但尚未有 RepoFix 真实模型评测集，因此上述流程属于待交付的实验设计。
